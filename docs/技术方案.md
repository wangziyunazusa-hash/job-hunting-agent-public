# Codex Job Hunting Agent 完整技术方案

## 目标与边界
模式 B：自动发现获准来源的岗位 → 基于真实事实库匹配 → 微调日语/英语简历 → 用户审阅 → 在明确允许的网站自动填写 → 用户自行最终提交。Phase 1 只实现本地手动导入、事实记录、去重、匹配和 UI；后续能力不是已实现功能。
原对话读取到的回答为引用占位符，本方案以本次用户指令为准。工作区现有私人简历没有读取或导入，事实库为空。

## 来源、权限与优先级
官方招聘网站 > LinkedIn = OpenWork。ATS 只有在经确认代表企业官方招聘渠道时归类 official；来源标签来自用户手动核实，Phase 1 不验证网站归属。

| 来源 | 读取策略 | 填写与提交 |
|---|---|---|
| 企业官网 | 逐站核对条款、权限、公开接口、限流；robots 不是授权 | 单独授权后才考虑字段填写；最终用户提交 |
| LinkedIn | 手动复制 JD 和链接；禁止未经授权抓取、浏览器自动化、Cookie 导出 | 不自动填写、不自动申请 |
| OpenWork | 按本项目约束仅手动导入，不推定有 API 权限 | 不自动填写、不自动申请 |
| Greenhouse | 获准 board 的 Job Board API GET；无认证 GET 不代表任意用途均获授权 | 不调用申请 POST |
| Lever | 获准企业的 Postings API GET，区分 global/EU | 禁用申请端点 |
| Ashby | 获准 job board 的 public posting API GET | 禁用申请端点 |

参考核对日期：2026-10-29。后续接入时须重新核对。

- [Greenhouse Job Board API](https://docs.greenhouse.io/job-board)

## 架构与技术栈
本地 Python 3.11+ / Streamlit / SQLite / pytest / Git。核心仅依赖标准库；UI 单独依赖 Streamlit。应用服务隔离持久化与展示，Phase 1 无网络客户端和模型 SDK。
后续由确定性编排器调度六个逻辑 Agent（不是当前并行运行的六个进程），使用 JSON Schema 校验输入输出。网络网关单独部署，按域名、接口、HTTP 方法授权；LLM 无网络和浏览器凭证。需要多人协作时迁移 PostgreSQL、对象存储和任务队列，不提前引入。

数据流：来源适配器/手动粘贴 → Import Service → SQLite 快照与来源 → Matching Service → 用户工作台。后续增加事实引用简历服务和受限表单填写服务。

## 数据模型与数据库 schema
以下前七张业务表和版本表已由 migrations/001_initial.sql 实现；字段类型和 CHECK 以该文件为准。

| 表 | 关键字段与关系 |
|---|---|
| schema_migrations | version 主键，重复启动幂等 |
| jobs | id, company, title, location, requisition_id, status, created_at |
| job_source_links | id, job_id FK, source, url UNIQUE, application_url, imported_at, method=manual |

后续迁移（Phase 1 不创建空壳业务）：
```sql
CREATE TABLE duplicate_candidates (
 id INTEGER PRIMARY KEY, left_job_id INTEGER REFERENCES jobs(id),
 right_job_id INTEGER REFERENCES jobs(id), reason TEXT NOT NULL,
 decision TEXT CHECK(decision IN ('pending','merge','separate')), reviewed_at TEXT);
CREATE TABLE resume_versions (
 id INTEGER PRIMARY KEY, job_id INTEGER REFERENCES jobs(id), language TEXT CHECK(language IN ('ja','en')),
 content TEXT NOT NULL, content_hash TEXT NOT NULL, facts_revision TEXT NOT NULL,
 status TEXT CHECK(status IN ('draft','review_required','approved','obsolete')), created_at TEXT);
CREATE TABLE resume_claims (
 resume_id INTEGER REFERENCES resume_versions(id), claim_id TEXT, fact_id INTEGER REFERENCES facts(id),
 original_text TEXT NOT NULL, revised_text TEXT NOT NULL,
 PRIMARY KEY(resume_id,claim_id,fact_id));
CREATE TABLE permissions (
 id INTEGER PRIMARY KEY, domain TEXT NOT NULL, action TEXT NOT NULL, endpoint_scope TEXT NOT NULL,
 evidence TEXT NOT NULL, approved_at TEXT, expires_at TEXT, revoked_at TEXT);
CREATE TABLE applications (
 id INTEGER PRIMARY KEY, job_id INTEGER REFERENCES jobs(id), resume_id INTEGER REFERENCES resume_versions(id),
 state TEXT NOT NULL, permission_id INTEGER REFERENCES permissions(id), payload_hash TEXT,
 approval_hash TEXT, user_reported_submitted_at TEXT);
```
后续事实变更要采用追加版本和撤销机制；当前事实界面只追加、不修改。简历批准绑定 JD、事实版本及正文摘要，任何变化使批准失效。

## 去重与官方优先
1. HTTPS 链接标准化：移除片段和明确的营销参数，保留岗位业务参数。
2. 相同来源 URL 幂等，JD 变化保留新快照。
3. 同一规范化公司 + 相同企业岗位编号或相同申请链接，视为强证据合并。编号必须由用户核实，不能填写平台自己的列表编号。
4. 同公司/标题/地点相同但无强证据，只显示人工核查提示，避免误合并同名不同岗位。不同语言标题、公司别名和模糊相似在 Phase 2 加候选关系，不自动合并。
5. 同一岗位优先读取官方快照，否则 LinkedIn/OpenWork 按最新导入快照，优先级相同。所有原始来源和快照保留。
6. Phase 1 展示该优先来源所附申请链接；官方未提供时保留空值，不臆造 URL。后续提供独立 preferred_application_link 回退规则和官方核验标记。

## 匹配与简历事实
事实由用户手动录入证据位置及日/英语内容，明确勾选确认后才用于匹配。不读取工作区历史简历，不推断用户能力。
Phase 1 识别有限词表（Python、SQL、日/英语、项目管理、产品管理、数据分析），计算已确认事实提及数/已识别 JD 词项数。无已识别词项返回 null，空事实返回 0 覆盖及未知提示。
覆盖是检索辅助，不是适岗评分；否定句、技能熟练程度、必选/加分、签证、工资、语言等级和年限均需人工核对。事实引用 ID 和 JD 摘要可追溯。
Phase 3 允许措辞和顺序微调；禁止新增技能、改日期/职称/学历、扩大职责、编数字。逐句 claim → fact_id 映射；日英表达均保留同一事实边界。缺口进入待补充清单，不能自动填充。

## 状态机
当前 jobs.status：imported → matched，可重复匹配；rejected/expired 为保留状态，不开放 UI 修改。没有申请提交能力。
后续 applications：discovered → normalized → matched → resume_draft → review_required → approved → fill_prepared → awaiting_user_submit → user_reported_submitted。
任何不确定进入 needs_information；失效进入 expired；用户放弃进入 rejected。只有用户审阅可批准；填写前重新核对权限、页面、字段与摘要。禁止任何 Agent 调用 submit；最终结果只能用户报告并标明未独立验证。

## 六个 Agent
完整可复用 Prompt 位于 prompts/01–06。每个 Prompt 包含目标、输入、输出、拒绝条件；编排器用代码验证权限与事实，不能依赖 Prompt 自律。Phase 1 未调用模型。

## 安全机制
默认拒绝网络与所有填写/提交动作；没有浏览器、Cookie、邮箱发送、申请 POST 能力。网络策略函数仅为后续边界示意，不能代替操作系统隔离。
JD 和网页是数据，提示注入不得改变系统指令、事实、工具权限。参数化 SQL、必填校验、长度上限、HTTPS 无凭证链接；URL 不请求、不解析 DNS。后续 HTTP 客户端还需 DNS/IP 和每次重定向校验防 SSRF。
本地数据库包含个人信息，Git 忽略 data、.env 和凭证；启动仅绑定 127.0.0.1，不应暴露公网。Phase 1 不提供磁盘加密或访问控制；使用系统磁盘保护，删除数据前手动备份。后续增加保留期限、加密备份、脱敏导出和删除功能。
审计日志记录事件及 ID；Phase 1 不是防篡改审计系统。依赖版本使用范围，尚未生成跨平台锁文件；发布前固定经过验证的依赖版本。

## 测试与验收
自动测试：迁移幂等、外键约束、空事实库、日英文本、来源与域名一致、URL 校验、幂等导入、历史快照、强证据去重、弱证据不误合并、官方优先、未确认事实排除、未知词项、词边界、注入作为文本、禁止网络/填写/提交。
UI 自动 smoke：使用 Streamlit AppTest 检查首屏、手动导入、事实保存与匹配按钮。所有测试使用临时数据库或空本地数据库，无真实网站请求。
人工验收：粘贴 JD → 保存 → 查看来源 → 增加真实事实并确认 → 查看覆盖和引用；检查数据库只在 data 下产生；确认界面无提交按钮。

## 分阶段路线图
Phase 1（当前）：独立 Git 仓库、AGENTS.md、数据库迁移、空事实库、手动导入、保守去重、有限词项匹配、Streamlit、测试及运行说明。
Phase 2：逐站授权登记，Greenhouse/Lever/Ashby GET 适配器，分页、限流、退避、缓存、下架检测；官方归属核验；候选重复审阅和别名映射。LinkedIn/OpenWork 仍仅手动导入。
Phase 3：接入可配置模型与结构化输出，事实版本控制、逐句引用、日英模板、硬信息锁定、差异审阅、批准哈希、导出 DOCX/PDF；专门测试事实变造与注入。
Phase 4：明确允许的站点独立表单适配器；预览每个字段、最小权限、停止开关、验证码和法律声明交给用户；任何可能提交的按钮和端点禁止执行。
每期以验收通过进入下一期；不启用持续后台搜寻，不生成定时自动化，不对外发布。
