# 岗位偏好与可解释排序

更新日期：2026-11-04。默认没有具体公司、权限或个人偏好，本次仅增加本地功能。

## 能做什么
用户保存一版求职偏好：目标职位关键词、地点关键词、希望 JD 出现的关键词，以及需要人工复核的词。每项按行输入，支持用户自己提供日英别名。每类最多 50 项，每项 100 字符；Unicode 标准化、大小写归一并去重。名称相同也会创建独立版本，不覆盖旧偏好。

偏好不是简历事实。输入“Python”只代表希望在 JD 看见 Python，不会证明用户掌握 Python、增加事实或改变已批准简历。

按偏好排序只处理本地已导入的有效、未合并岗位；被拒绝、已失效或合并隐藏的岗位不进入本次结果。LinkedIn/OpenWork 手动导入 JD 优先，缺失才回退官方。

在已有“采集已授权来源并匹配”中也能选择偏好。选择后，采集完成会生成排序快照；没有授权时仅处理本地岗位。没有持续后台任务或新增网络权限。

## 如何计算

明确显示两种不同指标：

- 偏好词项覆盖：配置了标题关键词则占一项，地点关键词占一项，每个希望 JD 出现的关键词各占一项。标题/地点在同类关键词中命中任意一个即算该项命中；JD 关键词逐项计算。分母只使用已知维度，未知地点不当作失败；全未知或未设置任何普通偏好时返回 null。
- 事实词项覆盖：沿用已有匹配引擎，只表示有限 JD 词项能否关联到已确认事实，返回原始事实 ID 和 JD 摘要。没有识别词项时是未知，不是零分。

职位、地点使用 jobs 中保存的元数据（目前是首次导入值），不会从 JD 自动提取或更新。地点为“未注明/unknown/not specified”时标未知；缺失别名时只说明没有字面命中，不能据此断定地区不符合。用户应核对实际 JD。

文字使用 NFKC/casefold 后进行字面匹配，ASCII 词有边界（如 PM 不匹配 PMP，SQL 不匹配 PostgreSQL）。不是语义理解，不自动识别东京/東京/Tokyo、远程工作范围、年限、签证、薪酬或否定句。

顺序：无复核词标记的岗位优先；随后偏好词项覆盖降序、事实词项覆盖降序，未知排在对应的已知指标之后，最后以岗位 ID 稳定排序。复核词命中只提示和后排展示，不会自动拒绝或删除岗位。比如“no overtime”也会命中 overtime，必须人工读上下文。

每条结果保留维度、原始观察值、命中词、复核词、匹配来源、来源 URL、JD 摘要、事实引用和偏好版本。没有录用概率、资格判定或自动提交动作。

## 筛选和历史

事实覆盖下限默认 0，复核词默认显示。用户可明确提高下限或隐藏复核词命中的岗位，界面显示每条隐藏原因；事实覆盖未知仍保留，不把未知视为失败。

排序快照存入 ranking_runs。岗位、状态、事实、当前 JD/来源或 API 可用状态变化时，历史快照显示 stale；需要用户重新计算。新偏好是独立版本，不会篡改旧快照。JSON 下载标明 stale 与摘要一致性状态，包含原始排序和理由，不是只下载当前筛选后的视图。

快照摘要用于一致性检查，不是签名；直接修改数据库并重算摘要仍可能篡改。排序不会改变事实，也不会使已批准简历仅因偏好改变而失效。

## 数据与事务

006_preferences.sql 新增 search_profiles 和 ranking_runs。profiles 保存偏好及摘要；runs 保存 profile_id、底层资料摘要、报告及报告摘要。排序与匹配报告使用同一事务快照；处理中发生异常会整体回滚本批匹配与排序。

全局上下文包含岗位/事实/来源信息及可用状态，是保守的失效判断。每次批量排序会保存匹配报告；当前没有自动清理，规模增大后需要增加保留策略与分页。
